# PitchMi — STATUS

## Current state
v1 core loop is built end-to-end (T-1150), now a **text-first flow** (T-10018): type or paste your script → the server seeds a first, disposable karaoke path from it → rehearse on camera against the prompter → evaluate → results, and **every take re-times the prompter to the user's own measured pace** by aligning what they said against what they wrote. There is no improvise-first take, no video upload path, no transcript editor, no speed slider and no pacing engine — to change the words you edit the text (which re-seeds the path), and to change the pace you just record again. **Server** (Express) exposes projects, script (seeds the path), evaluate (timing/accuracy scoring + re-timing + Gemini delivery eval via OpenRouter/Gemini), save, takes, ad stub, and admin — behind a fail-open kill switch, surge auto-trip, upload cap, JWT auth (Supabase JWKS ES256 with HS256 fallback), and RLS. **Client** (Next.js 15) implements the screens with anonymous Supabase auth, camera recorder, `performance.now()`-based karaoke teleprompter, results (Try again / Edit text / New video / OS Share — no cloud save, so my-videos is unlinked), and admin. The five product screens now carry a **release UI pass** (T-10022) and a **second visual pass** (T-10024): one semantic token layer in `globals.css`, a designed **dark theme that follows the OS** on every screen, a custom `VideoPlayer` in place of the browser's `<video controls>` on `/results`, a real desktop layout (two shared shell widths; `/results` is a genuine two-column grid at `lg`), a composer that fills the viewport, **one brand accent** (indigo, deliberately outside the green/amber/red score arc), and a written direction in `docs/design-direction.md` grounded in 21 real shipped products pulled from Refero. All automated acceptance checks pass. Not yet run: real external-API smoke (needs keys) and the manual browser checklist below.

- 2026-08-02 (T-10018): **Text-first flow** — the entry point is a script you type, and the prompter learns your pace from every take. **Why:** Eli's judgment after testing the record-first flow — *people cannot edit by speaking again*; to change one word you had to re-perform the whole thing. **The hard part:** karaoke needs a timestamp per word and typed text has none, and two previous attempts to synthesize those timings (T-1167, T-1168) were rejected as "too fast" / "not my rhythm" before T-1169 deleted the pacing engine outright. This does **not** rebuild it. **(A) `server/src/lib/scriptPath.js`, the core of the task.** `buildPathFromScript(scriptText, spokenWords)` tokenizes the typed script with the existing `segmentWords`, aligns it against the take's Scribe words with the **already-exported** `align()` from `score.js` (untouched — a Levenshtein DP whose zero-cost diagonals are exactly the anchors needed; note it never reads start/end, and a spoken filler can never anchor a typed word because `eq` refuses fillers), and gives every matched typed word the **exact** `start`/`end` of the moment it was really said. Only unmatched words (mis-heard, skipped, fumbled) get a computed time, and only by interpolation between two real neighbours in proportion to `charLen` — longer words take more of the gap. A leading run back-extrapolates at the matched region's measured rate floored at 0 (never spread across the whole leading silence, which would park the prompter on word 1); a trailing run prefers the audio that really is left after the last anchor and only extrapolates when there is none. `t_start` is then forced non-decreasing as a safety net, because the karaoke clock early-`break`s on the first word past `elapsed` and a single backwards step kills highlighting **silently**, with no error anywhere. Output goes through `buildSubtitles` verbatim, so the path is shape-identical to a spoken one and `scoreTake` reads it unchanged. `coverage = matched / typed-word-count` is returned so callers can tell a delivery of *this* script from an improvisation. **(B) `buildSeedPath(scriptText)`, ~40 disposable lines.** The very first take needs something to follow, so a script gets `SEED_CHARS_PER_SECOND` (13, **characters** per second — a WPM figure calibrated on English is wrong on Hebrew) plus the three fixed pauses carried over from T-1168 (80ms between words, 150ms after a clause break, 350ms after a sentence end). No anchoring, no stretching, no smoothing, no rate model; it survives exactly one take. **(C) `POST /api/script`** `{project_id, text}` → `{path, word_count, est_duration_s}`, auth'd, no media so no rate limiter and no media semaphore; `< 3` words → `400 script_too_short`, over `MAX_SCRIPT_CHARS` (1200, checked on the raw length — it also bounds the O(n·m) DP) → `400 script_too_long`, both with EN/HE messages. Writes `{script, path: seed}` via the existing generic `db.updateProject`, so **re-posting an edited script always resets to a fresh seed** — nobody ever rehearses against timings measured for different words. `projects.script`/`projects.path` are existing columns; no migration. **(D) `POST /api/evaluate` learns the pace.** After `scoreTake` — *strictly* after, so the take is judged against the path it actually followed, not one derived from itself — the take is realigned against `project.script`; at `coverage >= MIN_ALIGN_COVERAGE` (0.5) the re-timed path is persisted and returned as `path`, and below it the stored path is left exactly as it was and `path` is omitted. `coverage` + `retimed` ride on the evaluate event (numeric metadata only) so the threshold can be tuned from real data. **(E) Deleted:** `POST /api/transcribe` and its route file, its per-IP limiter (it guarded a route that no longer exists; `/api/evaluate` is now the only billable route and keeps its unchanged 30/h), the `/recorder` improvise-first screen, and the home drag-and-drop upload path. **(F) Client:** `/` is now a script screen — the use-case picker is unchanged, and beneath it a `dir`-aware textarea (Hebrew right-aligns as you type) with a live `~18s` estimate from new `lib/estimate.ts` (`WORDS_PER_MINUTE = 150`). Over 30s the estimate turns amber ("About 8 seconds over — trim it a little") and the tail past the 30-second mark is tinted in place via a mirror layer behind the textarea. Per Eli's ruling it **flags, it never blocks and never rewrites** — no AI shortening, no auto-trim, and over-length does not disable the button, because the estimate is an approximation and the real gate is the server's 30s cap on the actual take. `/wait` adopts a returned `path` so "Try again" rehearses at the measured pace; `/results` gains **Edit text** (deliberately *not* calling `reset()`, which would wipe the script it exists to keep) beside the unchanged Try again / New video / Share. `useRecorder.ts`, `middleware/upload.js`, `Prompter.tsx`, `score.js` and the scoring/eval pipeline are **byte-for-byte untouched**. - **`MIN_ALIGN_COVERAGE = 0.5` is a guess with no data behind it (T-10018).** Stated plainly because it gates a real product behaviour: below it, a take does **not** re-time the prompter. It was not derived from measurement — there was no corpus of real takes to derive it from. Every evaluate event now logs `scores.coverage` and `scores.retimed`, so the first week of real usage is exactly the dataset needed to set it honestly. Filed as `FU-COVERAGE-THRESHOLD`. Measured behaviour so far is synthetic only: in `scriptPath.test.js`, mangling every 2nd/3rd/5th word of a 12-word script yields coverage ~0.45/0.6/0.75 and in every case still produces a fully usable path — one word per typed word, monotonic, spanning real measured time, no two words sharing a start. So the interpolation degrades gracefully well below the threshold; what 0.5 actually decides is when the timings stop being *trustworthy enough to keep*, and that is the judgment no test can make.

- **Deviation (T-10018): the seed path re-attaches punctuation, then `buildSubtitles` strips it again.** `segmentWords` reports clause/sentence breaks as *flags* on a punctuation-free surface, while `buildSubtitles` (correctly, for spoken words) reads those hints off each word's **trailing punctuation**. Rather than change `buildSubtitles`, both script paths append a synthetic `.`/`,` before handing words over; it round-trips to the original surface. - **Deviation (T-10010), the important one — the container is identified by magic bytes, not by the declared mime.** The task specced a multer `fileFilter` allowing only `video/webm|mp4|quicktime|x-matroska`, with `-f` chosen from the mime-derived `inputExt`. Both halves are unshippable as written, and the evidence is in `tests/api.upload.mime.test.js`: multer 2.2/busboy **cannot parse** the Content-Type every real browser sends for a MediaRecorder blob (`video/webm;codecs=vp9,opus` — the unquoted comma is not a legal parameter value) and falls back to reporting `text/plain`. Measured: `video/webm;codecs=vp9,opus` → `text/plain`, `video/mp4;codecs=avc1.42E01E,mp4a.40.2` → `text/plain`, plain `video/webm` → `video/webm`. So (a) a strict video/* allowlist would have 415'd **every Chrome and Firefox take**, and (b) picking the demuxer from that mime would hand `-f matroska,webm` to an iOS mp4. Implemented instead: new `sniffContainer(buffer)` in `lib/audio.js` reads the EBML magic (`1A 45 DF A3`) or an ISO-BMFF `ftyp` box at offset 4, returns `'webm'|'mp4'|null`, and **null throws a 415 before ffmpeg is spawned**; that result drives both the temp filename and `-f`. The `fileFilter` survives as a cheap pre-buffer gate (it still rejects `text/html`, `application/vnd.apple.mpegurl`, …) but had to add `text/plain` + `application/octet-stream` to the allowlist for the reason above — it is explicitly **not** the authority, and the header is attacker-controlled anyway. This is strictly stronger than the specced design: a playlist declared `video/webm` is now rejected on its bytes. `extForMime` is deleted (dead once the sniff decides). Both real containers verified end-to-end through `extractAudio` **and** `transcodeForEval` with the actual ffmpeg binary (mp4 fixture + a webm muxed from it).
